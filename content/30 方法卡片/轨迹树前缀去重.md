**一句话**：一次执行会分叉成很多条轨迹，把它们按共享前缀拼成一棵树，再按优先级挑有限几条，公共前缀的 token 只贡献一次梯度。

## 为什么需要

黑盒 harness 跑长任务时会压缩历史、派子智能体、重试失败路径。这三件事都会让同一次执行产出多条互不相同的上下文路径。

把这些路径各自展开成一条训练样本，共享的前缀就会被重复训练很多遍。QWENGYRE 的案例里，一条执行的 10 条路径展开是 1,716 个节点出现次数，共享节点只有 1,347 个，多出来的 369 个全是重复。

反过来只取主轨迹也不行：子智能体推的子任务、摘要分支，都是有价值的策略输出，丢掉就少了信号。

所以需要一种表示，既保留分支，又不重复计前缀，还能控制一次执行贡献的样本量。

## 怎么做

**第一步，逐调用记账。** 记下每次请求的输入 token id、输出 token id、输出 token 的行为对数概率。工具调用的原始负载按 call id 缓存，匹配后续请求历史时先还原，否则 harness 对消息格式的重排会让本该命中的前缀匹配不上。

**第二步，拼树。** 每个请求记录是一个节点，存增量输入、输出、元数据。新请求进来时用序列化上下文在树上匹配已有路径，命中部分直接复用 token，只对新增内容编码；分叉开新枝，完全对不上的挂到根。

**第三步，按角色定优先级抽叶子。** 叶子连同根到叶的路径构成一条候选轨迹。按终止请求的角色分类，先抽高优先级的类：

$$
\text{main} > \text{main-summary} > \text{sub-agent} > \text{sub-agent-summary}
$$

- main：主智能体推进任务的轨迹，任务级奖励最直接记在它头上。
- main-summary：主智能体为腾上下文写摘要的那条，在管理上下文而不是推进任务。
- sub-agent：子智能体推进子任务的轨迹，只能通过被分派的子任务间接贡献。
- sub-agent-summary：子智能体的摘要轨迹，排最后。

**第四步，抽一条掩一段。** 每轮取还有未掩码可训练 token 的最高优先级类，按剩余可训练 token 数成比例抽一个叶子；抽中后把这条根到叶路径上的目标固定，再把整条路径掩码，保证公共前缀不被训练两次；下一轮用更新后的计数重新加权。抽到没有可训练 token 或凑满 $J_{\max}$ 为止。

**第五步，按执行归一化。** 设执行 $i$ 的最终目标集合为 $T_i$，$L_i=|T_i|$：

$$
L_i(\theta) = \frac{1}{L_i}\sum_{u\in T_i}\ell_u(\theta),\qquad
\mathcal{L}(\theta) = \frac{1}{BN}\sum_{q=1}^{B}\sum_{k=1}^{N}L_{i(q,k)}(\theta)
$$

先说它在算什么：把一条执行的所有可训练 token 平摊，再对 batch 里 $B$ 个 query 乘 $N$ 条执行求平均。

- $\ell_u(\theta)$：单 token 损失，带重要性权重与裁剪。
- $L_i$：这条执行计入损失的 token 总数，已去重。
- $B$：一个训练步的 query 组数。
- $N$：每个 query 的执行数。
- $i(q,k)$：第 $q$ 个 query 的第 $k$ 条执行。

分母取 $L_i$ 而不是「轨迹条数乘以每条的 token 数」，是为了让一条切出 5 条轨迹的执行，聚合权重与切出 1 条的执行相同。

## 适用边界

- 只在 rollout 时能拿到精确 token 与行为概率时才成立。拿不到原始 token（只有渲染后的文本）就没法做树上匹配。
- 优先级的四类顺序是对 Claude Code 的观察。换成树搜索、辩论、多角色流水线型 harness，这个顺序没有依据，得重新定。
- $J_{\max}$ 是超参，最优值随叶子数分布变化。QWENGYRE 在 NL2RepoBench 上测到 5 就够（与全收持平），换任务要重测。
- 树本身要存全部 token 片段，内存开销随执行规模涨。执行越长越要注意节点存储的压缩。
- 掩码会让部分 token 永远不进损失。如果某些关键决策只出现在被掩掉的那条路径里，就学不到。
